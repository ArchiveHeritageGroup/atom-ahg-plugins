# A PDF viewer exactly 300 pixels wide

Date: 2026-09-01
Release: atom-ahg-plugins v3.106.57
Reported by: Stefan du Toit, against the Wits Archaeological Collection instance

## The report

Opening a record on the collection displayed fine, but selecting a preview from the image
carousel gave a PDF viewer that "does not span the entire field that is designated for
it". Checked in two browsers, which ruled out a client-side quirk before anyone looked at
the code.

It read as a scaling problem. It was not.

## 300 is the tell

The viewer was full height and narrow. An `<iframe>` carrying no CSS width falls back to
the CSS specification's default of exactly 300px, so tall-and-narrow means width was lost
while height survived - two different mechanisms, not one broken calculation.

Height survived because the renderer emits it itself, per id, with the runtime value:

    #pdf-frame-iiif-viewer-5480-ca4f6ae5{height:500px;background:#525659;}

Width is static, so it lives in a class - `.ahg-pdf-frame { width: 100% }` in
`ahgIiifPlugin/web/css/viewer-switch.css`. The page never linked that stylesheet. None of
the six stylesheets it did load defined the class, and the only rule reaching the frame
was the height block above.

## Cause

In `render_iiif_viewer()`:

    if ($hasPdf) { ...; return $html; }         // line 450, exits here
    $html .= get_iiif_viewer_css($pluginPath);  // line 454, never reached

`get_iiif_viewer_css()` is what emits the `<link>`. The PDF branch returned four lines
above it. Every PDF record on every instance running this code was affected, not one
document.

The fix links the stylesheet before the branch and drops the duplicate call on the image
path.

## This is a successor to the CSP work, not a new class of bug

The August CSP work moved viewer geometry out of inline `style=""` attributes - which a
nonce can never cover - and into stylesheet classes. That was the right fix. It also
created a dependency that did not exist before: every render path must now link the
stylesheet, or the classes it defines are inert.

Mirador hit this at the time and was fixed. A comment directly above
`get_iiif_viewer_css()` describes the failure mode in so many words, including the
observation that OpenSeadragon escaped it only because its height came from a per-id
block rather than a class. The PDF branch has the same shape and returns before the link.
The note was written; the branch was not covered.

When geometry moves from an attribute into a class, enumerate the `return` statements
above the link - not just the call sites of the renderer.

## Verified

Counted on the live HTML rather than judged from the rendering:

    PSIS      pdf-document, pdf-viewer-multi-page   viewer-switch.css: 1  (was 0)
    PSIS      three image records                   viewer-switch.css: 1
    archaeology  Stefan's exact URL                 viewer-switch.css: 1  (was 0)
    archaeology  collection page, image record      intact
    error logs   both instances                     clean

The image records matter as much as the PDF ones: removing the second call site could
have left them with zero links and broken Mirador, or two and duplicated it.

Probe with `curl -sL`. These slugs 301 to the non-`/index.php` form, and measuring the
redirect reports zero matches for everything, which reads as a total outage.

## Deployment

Released from the canonical tree, then fetched and reset on archaeology - never
copy-and-commit. The tag was printed before and after the pull, because a fetch that
fails silently still lets `reset --hard` exit 0 with the tag unmoved:

    before  v3.106.56  df9a9b88   get_iiif_viewer_css at line 454
    after   v3.106.57  2f65c2ef   get_iiif_viewer_css at line 450

Ownership restored to www-data after the root-run reset; root-owned files under
`ProtectSystem=full` fail later in ways that look unrelated to the deploy.
