# callhub:alerts re-raised fourteen closed calls at the week boundary

**Date:** 2026-09-21
**Release:** plugins v3.106.114 (b36aa164)
**Calls:** CH-000118 to CH-000131 (all duplicates of closed calls). Pattern call: CH-000094.

## What happened

At 00:07 SAST on Monday 21 September, the hourly `callhub:alerts` tick raised fourteen
high-priority CallHub calls. Every one had `Occurrences: 1` and a last-seen date between
15 and 20 September. **Nothing new had occurred.** All fourteen were faults already
fixed and closed during the preceding week - including CH-000065 and CH-000066, the
original pair that opened the whole arc on the 17th.

The fourteen were really **seven faults, each filed twice** - once as the exception row
and once as the HTTP 500 row, the same structural pairing as CH-000065/066.

## The defect

`ahg_error_alert` has `UNIQUE (signature, period)`, claimed before the spool write, with
`period` an ISO year-week. That is deliberate: **one ticket per fault per week, and a
fault still failing the following week raises a fresh one.** Without it, a fault that
recurs months later would be swallowed by a timeless reference.

⚠️ **The claim expired whether or not the fault had recurred.** At the week rollover
every unresolved row became claimable again, so the task re-sent all of them. The ISO
week was never the bug - it is the noise control. The missing test was recurrence.

### What was NOT changed, and why

The obvious-looking fix is to key the fingerprint on the week the error OCCURRED rather
than the week it is REPORTED, in `/usr/local/bin/ahg-report-error` line 151. **That is
wrong on two counts.** A fault closed in W38 and still failing in W39 must raise again,
or the monitor goes silent; and that script is shared with bookings-watchdog, sync-probe
and the workbench notification watcher, so a change there lands on every reporter on the
host. It was left alone.

## The fix

`CallHubAlertService::hasRecurredSinceLastSent()`, gating each row in the drain loop:

```php
$lastSent = DB::table('ahg_error_alert')->where('signature', $row->signature)->max('sent_at');
$lastActive = $row->last_seen_at ?? $row->created_at ?? null;
return strtotime($lastActive) > strtotime($lastSent);
```

Three deliberate choices:

- **Compared on `signature` across ALL periods**, not on the fingerprint and not within
  the current period. A fingerprint comparison still misses a row whose fault key
  changed for an unrelated reason.
- **Fails open.** Any exception, a missing `sent_at`, or a null timestamp returns true
  and the fault reports. A monitor that fails closed stops reporting and looks exactly
  like a quiet estate - the worst failure this job can have.
- **Checked before the `--dry-run` branch**, so a dry run reports what would really be
  sent. A separate `$stale` counter keeps "already sent this period" and "not seen since
  last sent" distinct in the summary line.

## Verified

Simulated against live data before release, over the same 50-row window the task reads:

```
candidate_rows  would_send_AFTER_fix  suppressed_by_gate
            19                     0                  19
```

All nineteen carry `last_sent = 2026-09-21 00:07:02` - the rollover tick that produced
the fourteen calls - and every row's last activity predates it. Next Monday would have
re-sent all nineteen.

The real proof is next Monday 00:00 SAST passing with no batch. callhub-51 has parked a
note on CH-000094 to check it then.

## Also found, not fixed

`ahg_error_log.signature` is `utf8mb4_unicode_ci` and `ahg_error_alert.signature` is
`utf8mb4_0900_ai_ci`. Joining them in SQL fails with "Illegal mix of collations" unless
one side carries an explicit `COLLATE`. The PHP is unaffected, because it binds a
literal and the comparison takes the column's own collation - so this only bites someone
writing a query across the two tables, which is exactly what the verification above had
to do.

## The wider point

This batch was **not** the phantom-call pattern repeating. The earlier phantoms were
calls raised from stale rows generated by my own diagnostic probes; CallHub's diagnostic
windows (commit a997ab4) were built to stop those. These were calls raised from rows
that had **already been raised and closed**, re-admitted because the dedupe key changed
underneath them at midnight. **No diagnostic window would have prevented a single one of
the fourteen, because nobody was probing.** Prevention built for one failure mode does
not cover a different one that produces identical-looking noise.
